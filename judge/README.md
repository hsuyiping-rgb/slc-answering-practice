# 理答策略判定器（C01）

情境卡 C01 的 LLM 判定器。這是垂直切片裡**風險最高的一環**（`agents.md` 未驗證風險 #3：LLM 能否穩定分辨反問／轉問／深究），所以先做。

## 檔案

| 檔案 | 用途 |
|---|---|
| `../functions/prompt.md` | 判定器的 system prompt。**唯一的真相來源**，改判定行為就是改這份。<br>2026-09-03 從 `judge/` 搬到 `functions/`——deploy 只上傳 `functions/`，真相來源必須住在實際部署的那一份，否則測過的與線上跑的會悄悄走鐘 |
| `../functions/strategy.py` | 分支對映（`to_branch`）與幻覺偵測。同樣理由住在 `functions/`，本目錄的腳本從那裡匯入 |
| `testset.json` | 14 題測試集，取自或改寫自 503 公開課真實逐字稿 |
| `run_eval.py` | 評測腳本（純文字輸入），供應商無關（Gemini／Groq 可切換） |
| `run_e2e.py` | 半鏈路端對端：真實課堂音檔 → Whisper → 判定器 |

## 執行

```bash
python judge/run_eval.py --backend gemini --model gemini-3.7-flash --repeat 3
```

金鑰從環境變數讀（`GEMINI_API_KEY` / `GROQ_API_KEY`），**不寫進檔案、不進版控**。

|---|---|---|---|
| Gemini | **gemini-3.7-flash** | 3 次 | ✅ **14/14 全通過，四道硬性門檻全過** |

## 設計要點

### 分支對映在程式裡，不交給 LLM

LLM 只輸出 `strategy` 與三個 flag，`branch_id` 由 `to_branch()` 推導。理由是分支是**設計決定**，必須可預測、可測試；讓模型決定等於把設計權交出去。

低信心（`confidence < 0.5`）與 `gives_answer=true` 都在程式裡強制改道，不依賴模型自律。

### evidence_span 子字串驗證

模型必須回傳老師原話中**一字不差的連續片段**。評測會驗證它確實是輸入的子字串——這是最便宜的抗幻覺檢查，正式服務也要保留（不符則重試一次）。

## 調校過程中修掉的三個坑

1. **prompt 自相矛盾**：釐清的範例裡寫了「旁邊的人幫他說」，但那其實是轉引。模型照著做，第 4 題就錯了。
   → 移除該例，並新增「**先看要誰開口**」的前置判準：要求別人開口一律是轉引或轉問，即使目的是把內容弄清楚。
2. **代答判成釐清**：「你是說條件語句、推論訊息、解題邏輯對不對？」被讀成確認式的釐清。
   → 在 prompt 裡**列出小宇實際說過的每一個字**，讓模型可以比對。凡是老師講出小宇沒說過的答案內容，一律 `gives_answer=true`。抽象規則不夠，要給可比對的清單。
3. **測試集比設計本身更嚴格**：第 4 題「有人可以幫他嗎？」要求必須判成轉引，但規格 §7 明訂轉引與轉問在本卡都對映 B3。模型在兩者間跳動其實無害。
   → 放寬為只驗證分支。轉引／轉問的辨別力留待其他卡驗證。

## 已知限制

- **轉引 vs 轉問未經驗證**。本卡兩者同分支，測試集無法區分。這是 `agents.md` 未驗證風險 #3 的一半，仍然開放。
- **測試集只有 14 題，且全部由設計者自己寫**。通過不代表對真實老師的自由發言穩健。錄音鏈路接上後應收集真實輸入擴充測試集。
- **Groq 後端未經評測**（額度限制）。程式路徑可用，已修掉 Cloudflare 擋 urllib 預設 UA 的 403。

## 環境地雷

- Groq 走 Cloudflare，**urllib 的預設 User-Agent 會被擋成 403 error code 1010**。要自帶 `User-Agent` header。
- 本機終端機是 cp950，腳本已自行把 stdout 包成 UTF-8。

# 半鏈路端對端測試（2026-09-03）

`run_e2e.py`。用 503 公開課的原始錄音跑「音檔 → Whisper → 判定器」，測 `agents.md` 未驗證風險 #2：**Whisper 對講課語氣的辨識率，以及辨識錯字會不會讓判定翻掉**。

七個樣本全部通過（其中 E7 只驗證辨識，理由見下）。但**通過的意義有限**，真正的收穫是三個發現。

## 發現一：句子越短，辨識越糟——而真實理答的台詞就是短的

| 樣本 | 字數 | CER |
|---|---|---|
| E5「可不可以不要用算式，再告訴我一次」 | 27 | **8%** |
| E6「小賢講的我覺得很清楚⋯⋯」 | 33 | **12%** |
| E1「我沒有聽得很清楚⋯⋯」 | 50 | 21% |
| E7「水費？水費還是水量？」（4 秒視窗） | 8 | 25% |
| E3「有人可以幫他嗎」 | 7 | 71% |
| E4「好，然後？」 | 4 | 100% |

長句幾乎沒問題，短句是災難。而 handoff 早就記過「**真實理答的台詞極短**：再一次／還有沒有／回到題目」——**最有價值的教學時刻，正好是最難辨識的**。這個矛盾是本系統的結構性風險，不是可以靠調參解決的。

## 發現二：Whisper 的提示詞會「順稿」，必須關掉

E7 的「水費？**水費**還是水量？」之所以是反問，關鍵在那個**重複**——先把學生的答案原樣丟回去，再並排選項。實測：

| 條件 | 辨識結果 |
|---|---|
| 4 秒視窗，無提示詞 | 「水費 還是水量」← 重複不見了 |
| 7 秒視窗，無提示詞 | 「省下多少?**水費水費**還是水量?水量」← **CER 0%** |
| 7 秒視窗，**有**提示詞 | 「省下多少?水費還是水量?」← 重複又被磨掉 |

**提示詞會把重複、口吃、不流暢磨平，而那些正是理答判定的依據。** 這與做講者重建時踩到的是同一個坑（提示詞在安靜片段會誘發幻覺）。

→ **實作決定：Whisper 呼叫一律不帶提示詞。**

## 發現三：不可修剪錄音前後的靜音

同一句話，視窗從 4 秒放寬到 7 秒，CER 從 25% 降到 0%。Whisper 需要前後文才能穩定解碼短句。

→ **實作決定：整段錄音原樣送出，前端不做靜音修剪、不做 VAD 切段。**

## 兩個測不到的地方（誠實記錄）

- **E4「好，然後？」在遠場錄音裡切不乾淨**：它夾在師生快速交替之間，加寬視窗只會吃進更多別人的話。這裡驗證的其實是另一件事——**辨識結果無意義時，系統走了 RETRY 而不是亂猜**（判定器輸出「其他」→ RETRY）。這是好消息，但不等於驗證了短句辨識。
- **E7 無法驗證判定**：放寬視窗後片段同時錄進學生的「省下多少」與「水量」，判定器把答案當成老師講的而判代答。**遠場課堂錄音切不出單一講者**，端對端的後半段要等產品情境的實錄才能測。

## 還沒測到的（風險 #2 只完成一半）

課堂遠場錄音是**比產品更嚴苛**的條件（回音、學生雜音、多人重疊）。產品情境是老師戴耳機麥克風、獨自在安靜房間說話，數字應該會好很多。

**下一步需要一段真實的產品情境錄音**：使用者戴麥克風，照著測試集念幾句理答，特別是短句（「好，然後？」「還有沒有？」「再一次」）。那才是風險 #2 的正式驗收。

# 風險 #2 正式驗收：產品情境錄音（2026-09-03）

`run_mic.py`。使用者本人對 Logi C270 網路攝影機麥克風錄 17 句（清單見 `recordings/錄音清單.md`），安靜房間、單人說話。**14/15 判定通過。**

## 結論：短句不是問題，先前的判斷要更正

| | 課堂遠場 | 產品情境 |
|---|---|---|
| **A 組極短句平均 CER** | **71–100%** | **7%** |
| R10「我沒有聽得很清楚⋯⋯」 | 21% | **0%** |
| R11「回到題目來⋯⋯」 | 27% | **0%** |
| R14 蓋章負向樣本 | 12% | **0%** |

「還有沒有」「為什麼」「再一次」「你從哪裡知道」全部 **CER 0%**，判定 5/5 通過。

> ⚠️ **更正**：前一節「發現一」說短句是**結構性風險**，那是錯的。課堂遠場的 71–100% 來自**遠場拾音與多人重疊**，不是句長。產品情境（單人、近場、安靜）下短句完全可用。

## 發現四：靜音會讓 Whisper 產生幻覺 ★ 最嚴重

15 秒安靜送進 Whisper，吐出 **「多謝您的收看」**。這與講者重建時在 506 國語逐字稿看到的「請訂閱 打賞支持明鏡」是同一類污染。

**等待是本系統的核心教學點。** 若靜音變成一句幻覺文字，判定器會把它當成某種策略，而不是走 WAIT——那等於系統告訴老師「你剛剛說了話」，而他其實正確地保持了沉默。

### 靜音閘門的設計：不能用絕對音量

| 檔案 | 幀 RMS 中位數 | P95 | **P95／中位數** |
|---|---|---|---|
| R17（15 秒安靜） | 0.0095 | 0.0107 | **1.1** |
| 16 個語音樣本 | 0.0096–0.0110 | 0.034–0.101 | **3.4–10.6** |

底噪中位數在所有檔案幾乎相同（~0.010），而 R17 的整體 RMS 是 0.0091——**跟語音只差 2.3 倍，絕對閾值換一支麥克風就失效**。

改看**起伏比**（幀級 RMS 的 P95／中位數）：語音有明顯高低起伏，底噪是平的。閾值 `DYNAMIC_MIN = 2.0`，兩邊各有 3 倍以上餘裕。17 個樣本全部判對。

→ **實作決定：送 Whisper 前先跑靜音閘門，判定為靜音就直接走 WAIT，不呼叫 API**（同時省一次費用）。另備 `looks_hallucinated()` 做第二道防線，比對已知的幻覺句型。

## 發現五：一個字錯掉就足以翻轉策略判定

R16「水費？水費還是水量？」被辨識成「水**肺**水**肺**還是水量」。**重複有保留**（印證發現三），但 `費→肺` 一個字之差，判定就從**反問**翻成**提示**。

這題保留為失敗項，不調鬆——它是「辨識層品質直接決定判定層正確性」的具體證據。（附帶一提，R16 取自課堂的另一個時刻，而判定器的固定情境是 C01 的三個欄位，本來就缺少「水費」的脈絡；在 C01 自己的詞彙範圍內不會有這個問題。）

## 順帶修掉的量測錯誤

第一次跑出來 A 組平均 CER 37%，是**我的量測有問題**：Whisper 有時輸出簡體（「还有没有」「为什么」），內容完全正確，但 CER 把每個簡體字都算成錯誤。加上 `opencc` 的 s2twp 正規化後，A 組從 37% 降到 **7%**——真實數字。

判定器本身不受影響（簡體輸入照樣判對），但**評測指標若不做繁簡正規化就會嚴重虛高**。

## 還沒測到的

- **耳機麥克風**。本機只有網路攝影機的麥克風（離嘴巴有距離，較接近筆電內建麥克風的條件），這批數據同時涵蓋了風險 #1 的一半。耳麥的表現只會更好，但沒有實測。
- **真實環境的干擾**：回音大的房間、背景有人講話、冷氣聲。這次是安靜房間。

- **`requests` 在這台機器上連不出去，`urllib` 可以**。這台有做 TLS 攔截的東西（防毒或代理），
  根憑證進了 Windows 憑證存放區但不在 `certifi` 的憑證包裡。urllib 會讀系統存放區所以沒事，
  `requests` 只認 certifi，一律 `SSLError: UNEXPECTED_EOF_WHILE_READING`。
  雲端沒有這個中間人，所以**只擋本機測試**——但 `functions/` 因此一律用 urllib，與全專案一致。
  註：`requests` 仍需安裝，它是 `firebase-admin` 的相依套件，只是我們不拿它發外部請求。
- **Gemini 的金鑰不要放 query string**。放了之後網址會連同 key 一起出現在例外訊息與
  Cloud Logging 的堆疊裡，等於自己把金鑰寫進日誌。改用 `x-goog-api-key` header。

## 本機 emulator 跑 functions（2026-09-21，不需 Blaze）

前端在 `localhost` 會自動改打 `127.0.0.1:5001`（見 `public/config.js`），所以 emulator 跑起來就能做完整的
錄音 → Whisper → 判定。兩支函式都在 emulator 裡實際打通過 Groq 與 Gemini。啟動：

```

python -m http.server 8765 --directory public      # 另一個視窗；然後開 http://localhost:8765
```

在這台機器上踩到的三個坑，**換電腦要重做前兩個**：

- **金鑰**：emulator 從 `functions/.secret.local` 讀 SecretParam（`KEY=value` 一行一把），已加入 `.gitignore`。
- **中文路徑讓 Python emulator 起不來**（`can't open file 'G:\ufffd...serving.py'`）。firebase-tools 用**空環境變數**
  執行 venv 的 python 取 SDK 路徑，中文 Windows 的 stdout 是 cp950、node 端卻用 UTF-8 解碼。
  修法：在 `functions/venv/Lib/site-packages/sitecustomize.py` 放 `sys.stdout.reconfigure(encoding="utf-8")`
  （venv 不進版控，所以這個檔要手動補）。`chcp 65001`、`PYTHONUTF8=1`、目錄接合點都**沒用**——
  環境變數傳不進去，接合點會被 realpath 解回中文路徑。
- **探索逾時**：GDrive 上的 venv 冷啟動超過 10 秒，預設的探索逾時會先放棄，症狀是 emulator 顯示 ready 但
  「valid functions are: 」是空的。用 `FUNCTIONS_DISCOVERY_TIMEOUT=180` 拉長。
- 順帶：在 Git Bash 用 curl 直接打中文 JSON 會被轉成 cp950，後端 `get_json` 解不開就回 WAIT——不是後端壞掉，
  把 body 寫成 UTF-8 檔案再 `--data-binary @file` 即可。

### 驗收時修掉的兩個 bug（`public/app.js`）

- **`wait_sec` 一律記成 0**（ratio 上千時）。開口門檻原本是「中位數 × 2」，但 Chrome 剛拿到麥克風時前幾幀是
  數位零，中位數趨近 0，2 × 0 還是 0，第一幀底噪就被當成開口。連續四輪 ratio 6000–9000、wait 全是 0。
  修法：門檻改成 `max(中位數 × 2, P95 × 0.3)`，且 `ONSET_RUN` 從 3 幀（60 ms）拉到 10 幀（200 ms）——
  3 幀擋不住清喉嚨與滑鼠聲（拉到 P95 × 0.25 後仍把等 20 秒記成 4 秒、8 秒；使用者靜坐不動才準）。
  合成訊號驗證：0.5 s 數位零 + 7.5 s 底噪 + 2 s 語音 → wait 8；10 s 全底噪 → silent。
- **「再練一次」沒清事前自選的策略**，上一輪的選擇會被拿來對照下一輪。`reset()` 現在清 `preselect` 與 chip 樣式。

### 修正：`verbose_json` 的 `no_speech_prob`＋擴充幻覺清單（`functions/strategy.py`）

以合成音檔探測 Groq `whisper-large-v3`（底噪、點擊、C05 語音尾段當喇叭回音；老師句用 edge-tts `zh-TW-YunJheNeural`）：

| 組 | 樣本 | `no_speech_prob` | Whisper 吐的字 |
|---|---|---|---|
| 靜默＋干擾 | 15 | 0.106–0.527 | 響鐘（最多）、謝謝大家、請按讚訂閱分享、按下訂閱點讚訂閱、喇叭尾音被聽成一串話 |
| 老師講話 | 17 | 0.006–0.113 | 最高兩個是單字句「嗯？」（聽成「安」）與「水費？」（聽成「水肥」） |

兩組重疊，單靠機率切不乾淨，所以兩道擇一：
- 每一段 `no_speech_prob` 都 ≥ **0.2** → 靜默（講話組最高 0.113）
- 幻覺清單：子字串比對加「訂閱／按讚／點讚」；**整句比對**加「響鐘／謝謝大家」（老師可能真的說「謝謝大家」，只有整段只有這句才算）

離線：靜默 14/15 攔下、講話 17/17 不誤傷、五張卡測試集老師句 0 誤傷。唯一漏網的是**喇叭把學生語音大聲回送**
（「要換色」，0.194）——那是真的人聲，後端分不出來，靠耳機或 `echoCancellation`。

前端同步修：後端回 `silent` 時，`wait_sec` 改記整段長度（原本記的是閘門的開口點，也就是尾音或點擊聲的時間，會顯示「等了 0 秒」）。
